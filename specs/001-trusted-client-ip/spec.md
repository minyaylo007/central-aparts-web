# Feature Specification: Доверенный IP гостя из X-Forwarded-For

**Feature Branch**: нет (Spec Kit без git-расширения; работа в `master`, папка `specs/001-trusted-client-ip/`)

**Created**: 2026-09-11

**Status**: Clarified

**Input**: User description: "Сайт передаёт бек-офису IP гостя (заголовком X-Forwarded-For) на двух вызовах — котировка с купонным телефоном и проверка купона, — чтобы лимиты частоты в бек-офисе считали попытки по гостю. Сейчас адрес гостя берётся из ПЕРВОГО элемента X-Forwarded-For — его подделывает любой клиент одной строкой, и лимит перебора купонов обходится. Нужно: брать адрес гостя с учётом числа доверенных прокси перед сайтом (N-й элемент справа), N задаётся настройкой окружения."

## Контекст

Бек-офис ограничивает частоту проверок купона постоянного гостя по паре «телефон + адрес» и по
одному адресу. Адрес гостя ему сообщает сайт: на двух вызовах — котировка с купонным телефоном
(`/api/quote/<apt_id>`) и проверка купона (`POST /api/coupon/check`) — сайт кладёт адрес гостя в
исходящий заголовок X-Forwarded-For. Сейчас этот адрес — первый (левый) элемент входящего
X-Forwarded-For, то есть значение, которое клиент вписывает сам. Подставив в каждый запрос новое
выдуманное значение, клиент каждый раз попадает в новое «ведро» лимита и перебирает купоны без
ограничения.

Прокси, которыми управляем мы, дописывают или ставят адрес справа. Поэтому надёжный адрес —
N-й элемент справа, где N — число доверенных прокси перед сайтом. N зависит от топологии, поэтому
задаётся настройкой окружения `TRUSTED_PROXY_COUNT`.

### Топологии, которые обязана разобрать фича

| | Цепочка | Что приходит в заголовке к сайту | Статус сведений | N |
|---|---|---|---|---|
| (а) | гость → CloudFront → Lambda (прод сегодня) | по документации AWS CloudFront **дописывает** адрес зрителя к присланному клиентом значению: `<что прислал клиент>, <адрес зрителя>` | **не измерено** | не задаётся (вне фичи, см. «Ограничения») |
| (б) | гость → Caddy → gunicorn (коробка) | ровно одно значение — адрес соединения: Caddy 2.11 при пустом `trusted_proxies` заменяет заголовок, плюс явный `header_up X-Forwarded-For` | измерено 10.09 | 1 |
| (в) | гость → Caddy → nginx (realip) → gunicorn (коробка) | ровно одно значение: nginx перезаписывает заголовок адресом гостя, восстановленным realip | конфиг «в стол», не установлен | 1 |
| (г) | клиент → gunicorn напрямую (разработка, тесты) | что прислал клиент, или ничего | — | 0 |

## Clarifications

### Session 2026-09-11

Вопросы задавались дирижёру «🌐 Сайт бронирования — дирижёр»; все пять ответов — по рекомендации
спецификатора, плюс два уточнения дирижёра.

- Q: Чем разбирать адрес — werkzeug ProxyFix или своим разбором? → A: Свой разбор в `app.py`
  (`_visitor_ip`); схема, хост, порт, префикс и `request.remote_addr` не трогаются, ProxyFix не
  ставится (FR-013; обоснование — `research.md`).
- Q: Что делать при N ≥ 1, если элементов меньше N, заголовка нет или N-й справа — не IP? → A:
  Откат к адресу соединения + одна WARNING-строка с кодом причины (FR-006, FR-009).
- Q: Что писать в журнал без адресов гостей? → A: INFO о режиме при старте; WARNING при откате с
  кодом `no_header` / `fewer_than_n` / `not_ip` и числом элементов, без адресов и без содержимого
  заголовка; не больше одной строки на запрос, без трейсбека; обязательный тест «ни одного
  тестового адреса в журнальном выводе» — и на старте, и на откате (FR-009, FR-010, SC-003).
- Q: Что делать при неверном значении настройки (не целое, отрицательное)? → A: Стартовать в
  режиме по умолчанию (FR-002) и писать при старте ERROR-строку без значения настройки (FR-008).
- Q: Как назвать настройку и что значат «пусто» и 0? → A: `TRUSTED_PROXY_COUNT`, читается в
  `config.py` по образцу остальных полей класса `Config`; не задана/пусто — как сейчас (первый
  элемент), 0 — заголовок игнорируется, N ≥ 1 — N-й справа; для коробки (б) и (в) в README —
  N = 1 (FR-001–FR-004, FR-012).
- Уточнение дирижёра: находка `wsgi_adapter.py:57-58` (на Lambda `REMOTE_ADDR` = первый элемент
  X-Forwarded-For) — вне фичи; в спеке — явное ограничение: при N ≥ 1 на Lambda откат из FR-006
  падает на этот подделываемый адрес (раздел «Ограничения»).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Подделка заголовка не обнуляет лимит купонов (Priority: P1)

Владелец запускает сайт за прокси, которыми управляет сам (коробка, топологии (б) и (в)), и
задаёт `TRUSTED_PROXY_COUNT=1`. Злоумышленник шлёт серию проверок купона и котировок с купонным
телефоном и в каждую подставляет свой выдуманный X-Forwarded-For. Бек-офис получает от сайта во
всех этих запросах один и тот же адрес — адрес, поставленный прокси, — и лимит срабатывает после
положенного числа попыток.

**Why this priority**: ради этого фича и затевается — сегодня лимит перебора купонов обходится
одной строкой заголовка. На коробке он закрыт только тем, что прокси перезаписывает заголовок, —
защита держится на одной ланке и молча исчезает при смене цепочки.

**Independent Test**: тестовый клиент шлёт в сайт запросы с разными подделанными левыми
элементами и одинаковым правым; проверяется, что в подменный бек-офис на обоих вызовах уходит
правый (N-й справа) элемент.

**Acceptance Scenarios**:

1. **Given** N = 1 и во входящем заголовке `198.51.100.23, 203.0.113.7`, **When** гость
   проверяет купон, **Then** бек-офис получает адрес `203.0.113.7`.
2. **Given** N = 1 и во входящем заголовке `203.0.113.7`, **When** гость запрашивает котировку
   с купонным телефоном, **Then** бек-офис получает адрес `203.0.113.7`.
3. **Given** N = 1, **When** семь запросов проверки купона приходят с одинаковым правым элементом
   и семью разными левыми, **Then** во всех семи бек-офис получает один и тот же адрес.
4. **Given** N = 2 и во входящем заголовке `198.51.100.23, 203.0.113.7, 192.0.2.10`, **When**
   гость проверяет купон, **Then** бек-офис получает адрес `203.0.113.7`.
5. **Given** N = 0 (прокси перед сайтом нет, топология (г)), **When** клиент присылает любой
   X-Forwarded-For, **Then** заголовок игнорируется и бек-офис получает адрес соединения.
6. **Given** N = 1 и два гостя с разными адресами за одной цепочкой, **When** оба проверяют
   купон, **Then** бек-офис получает два разных адреса.

### User Story 2 - Без настройки ничего не меняется (Priority: P1)

Владелец не задаёт `TRUSTED_PROXY_COUNT` (так будет на проде — Lambda — до отдельного решения).
Сайт передаёт бек-офису ровно тот же адрес, что и до фичи: первый элемент X-Forwarded-For, а при
его отсутствии — адрес соединения.

**Why this priority**: решение владельца от 11.09 — без явной настройки прод не меняется.
Выкат кода на Lambda не должен сам по себе ни чинить, ни ломать лимиты.

**Independent Test**: матрица входящих заголовков прогоняется без настройки; переданный бек-офису
адрес совпадает с тем, что даёт нынешний разбор, для каждого входа.

**Acceptance Scenarios**:

1. **Given** настройка не задана и во входящем заголовке `203.0.113.7, 192.0.2.10`, **When** гость
   проверяет купон, **Then** бек-офис получает `203.0.113.7` (как сейчас).
2. **Given** настройка не задана и заголовка нет, **When** гость запрашивает котировку, **Then**
   бек-офис получает адрес соединения (как сейчас).
3. **Given** настройка задана пустой строкой, **When** гость проверяет купон, **Then** поведение
   то же, что при незаданной настройке.
4. **Given** любое значение настройки (не задана, 0, 1, 2, неверное), **When** запрашиваются
   `/robots.txt` и `/sitemap.xml`, **Then** схема и хост ссылок в них те же, что до фичи.

### User Story 3 - Эксплуатация видит режим разбора, но не видит адресов (Priority: P2)

Владелец или дежурная сессия по журналу понимают, в каком режиме работает разбор адреса (по
умолчанию или с каким N), и замечают, если настройка неверна или разбор регулярно откатывается.
Ни один адрес гостя в журнал при этом не попадает. В документации выката объяснено, какое N
ставить в какой топологии и почему.

**Why this priority**: неверное N не даёт ни ошибки, ни падения тестов — только тихо сломанный
лимит (все гости в одном ведре или подделка снова проходит). Без сигнала в журнале это не
заметить; без документации — не выбрать N правильно.

**Independent Test**: запуск с разными значениями настройки; проверяются записи логгера
приложения о режиме при старте, запись об откате и отсутствие адресов во всём журнальном выводе
тестов.

**Acceptance Scenarios**:

1. **Given** N = 1, **When** процесс приложения стартует, **Then** логгер приложения выдаёт одну
   запись уровня INFO о режиме разбора с N = 1 и без единого адреса (попадёт ли INFO в журнал
   коробки — см. FR-010).
2. **Given** настройка = `abc` или `-1`, **When** приложение стартует, **Then** сайт работает в
   режиме по умолчанию (FR-002), а в журнале одна ERROR-строка о неверной настройке — без самого
   значения и без адресов.
3. **Given** N = 1 и во входящем запросе заголовка нет, **When** гость проверяет купон, **Then**
   бек-офис получает адрес соединения, а в журнале ровно одна WARNING-строка с кодом `no_header`
   и числом элементов 0, без адресов и без трейсбека.
4. **Given** N = 2 и во входящем заголовке один элемент, **When** гость запрашивает котировку,
   **Then** откат к адресу соединения и одна WARNING-строка с кодом `fewer_than_n` и числом
   элементов 1.
5. **Given** N = 1 и во входящем заголовке `unknown`, **When** гость проверяет купон, **Then**
   откат к адресу соединения и одна WARNING-строка с кодом `not_ip`.
6. **Given** документация выката, **When** владелец выбирает N для топологий (б) и (в), **Then**
   он находит в README выката (вне репо) и `deploy/site.env.example` значение 1 и его обоснование.

### Edge Cases

- В заголовке меньше элементов, чем N (в том числе ноль — заголовка нет или он пустой): откат к
  адресу соединения, код `fewer_than_n` или `no_header` (FR-006).
- Элемент на позиции N справа — не адрес IPv4/IPv6 (мусор, `unknown`, адрес с портом, адрес в
  квадратных скобках): откат к адресу соединения, код `not_ip` (FR-006).
- Пробелы вокруг элементов и пустые элементы между запятыми: отсчёт справа ведётся по непустым
  элементам после обрезки пробелов.
- Несколько заголовков X-Forwarded-For в одном запросе: склеивать их через запятую — дело
  WSGI-сервера до приложения (gunicorn, Function URL); приложение видит одну строку и считает
  справа по ней. Склейка сервером в фиче не проверялась и отдельным тестом не покрыта.
- IPv6-адреса (`2001:db8::1`) — обычные элементы, отсчитываются так же.
- Адрес соединения тоже отсутствует: адрес гостя — пустая строка (заголовок в бек-офис не
  уходит, как и сейчас).
- Два разных гостя за одной и той же цепочкой при N = 1 получают разные адреса (не «все в одном
  ведре»).
- На Lambda откат к адресу соединения не защищает — см. «Ограничения».

## Ограничения

- **Lambda (топология (а)): N ≥ 1 не включать, не прочитав этот пункт.** На Lambda адрес
  соединения, который видит приложение, выставляет `wsgi_adapter.py:57-58`: если во входящем
  событии есть X-Forwarded-For, `REMOTE_ADDR` = его **первый** элемент, то есть значение,
  которое пишет сам клиент; только без заголовка — `sourceIp` события. Значит, при N ≥ 1 на
  Lambda откат из FR-006 (элементов меньше N, N-й справа не IP) падает на **подделываемый**
  адрес — защита в этих случаях не работает. Кроме того, сколько элементов дописывает цепочка
  CloudFront → Function URL, не измерено. Поэтому выбор N и выкат на Lambda — вне фичи, только с
  отдельного «да» владельца; `wsgi_adapter.py` фича не меняет.
- Защита на коробке по-прежнему требует, чтобы прокси ставили заголовок одним значением; фича
  убирает зависимость «сайт верит самому левому», но не заменяет обязательный эксперимент из
  README выката (вне репо) после любой смены топологии.
- На коробке журнал не настроен (нет конфигурации журнала ни в коде, ни у gunicorn): записи
  уровня INFO, включая строку режима из FR-010, туда не попадают — как уже сегодня не попадают
  строки `quote`; WARNING и ERROR видны. Настройка журнала коробки — вне фичи (research.md R3).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Сайт MUST определять адрес гостя по настройке окружения `TRUSTED_PROXY_COUNT` (N),
  которая читается один раз при старте в `config.py` по образцу остальных полей класса `Config`.
- **FR-002**: Если настройка не задана или задана пустой строкой (после обрезки пробелов), сайт
  MUST определять адрес гостя ровно так, как до фичи: первый элемент X-Forwarded-For после
  обрезки пробелов; если он пуст — адрес соединения; если и его нет — пустая строка.
- **FR-003**: При N ≥ 1 сайт MUST брать N-й элемент X-Forwarded-For, считая справа, из списка
  непустых элементов после разбиения по запятым и обрезки пробелов.
- **FR-004**: При N = 0 сайт MUST игнорировать X-Forwarded-For и брать адрес соединения (если его
  нет — пустая строка), без журнальной записи на запрос.
- **FR-005**: Один и тот же разбор MUST применяться в обоих местах, где адрес гостя уходит в
  бек-офис: котировка (`/api/quote/<apt_id>`) и проверка купона (`POST /api/coupon/check`).
  Других потребителей адреса гостя фича не добавляет.
- **FR-006**: При N ≥ 1, если заголовка нет или в нём ноль непустых элементов (`no_header`),
  элементов меньше N (`fewer_than_n`) или элемент на позиции N справа не является адресом
  IPv4/IPv6 (`not_ip`), сайт MUST откатиться к адресу соединения (если его нет — пустая строка).
- **FR-007**: Разбор адреса MUST NOT менять схему, хост, порт и префикс пути запроса: ссылки в
  `/robots.txt` и `/sitemap.xml` (строятся от адреса запроса) остаются такими же, как до фичи, во
  всех топологиях (а)–(г) и при любом значении настройки.
- **FR-008**: Если настройка задана, но неверна (не целое неотрицательное число из цифр 0–9 или
  отрицательное число), сайт MUST стартовать в режиме по умолчанию (FR-002) и записать при
  старте одну ERROR-строку о неверной настройке, не включающую само значение настройки.
- **FR-009**: При каждом откате из FR-006 сайт MUST записать ровно одну WARNING-строку на запрос:
  код причины (`no_header` / `fewer_than_n` / `not_ip`) и число непустых элементов заголовка,
  без трейсбека. Ни эта строка, ни любая другая журнальная запись сайта (старт, откат,
  существующие строки `quote` и `coupon_check`) MUST NOT содержать адрес гостя — ни целиком, ни
  частично — и содержимое X-Forwarded-For.
- **FR-010**: При старте каждого процесса приложения сайт MUST выдавать в логгер приложения одну
  запись уровня INFO о режиме разбора адреса гостя: «по умолчанию (первый элемент)», «заголовок
  игнорируется (N = 0)» или «доверенных прокси N = <число>» (при нескольких воркерах — по одной на
  воркер). Запись не содержит адресов. Попадание INFO в журнал коробки зависит от настройки
  журнала, которой сейчас нет, и вне фичи (раздел «Ограничения»); на Lambda INFO видна.
- **FR-011**: Тесты MUST покрывать матрицу топологий (а)–(г) для обоих вызовов из FR-005 при
  значениях настройки «не задана», 0, 1, 2 и неверном (ожидаемые адреса — research.md R7);
  прежние тесты, закрепляющие «первый элемент» (`tests/test_coupon_ui.py`, класс
  `TestClientIpForwarding`), MUST остаться верными для режима по умолчанию и дополниться
  случаями с N. Отдельный тест MUST проверять, что в журнальном выводе при старте и при откате
  нет ни одного тестового адреса.
- **FR-012**: README выката (вне репо) и `deploy/site.env.example` MUST описывать `TRUSTED_PROXY_COUNT`:
  что значит «не задана», 0 и N ≥ 1; N = 1 для топологий (б) и (в) и почему; почему на Lambda (а)
  N не выбрано и откат к адресу соединения там не защищает (раздел «Ограничения»); и что
  эксперимент из раздела «Після будь-якої зміни топології» остаётся обязательным.
- **FR-013**: Разбор MUST быть собственной функцией сайта, затрагивающей только адрес для
  бек-офиса: сайт MUST NOT подключать промежуточный слой, переписывающий окружение запроса
  (werkzeug ProxyFix и аналоги), и MUST NOT менять `request.remote_addr`.

### Key Entities

- **Настройка `TRUSTED_PROXY_COUNT` (N)**: «не задана» (включая пустую строку), целое ≥ 0, или
  неверное значение (→ режим по умолчанию). Задаётся окружением процесса, читается один раз при
  старте.
- **Режим разбора**: «по умолчанию» / «заголовок игнорируется» (N = 0) / «N доверенных прокси»
  (N ≥ 1). Определяется настройкой при старте, не меняется до перезапуска.
- **Адрес гостя**: строка с адресом IPv4/IPv6, либо (в режиме по умолчанию — как сейчас) первый
  элемент заголовка без проверки, либо пустая строка. Вычисляется на запрос, нигде не хранится и
  не журналируется; уходит только в исходящий заголовок к бек-офису.
- **Цепочка X-Forwarded-For**: входящий заголовок, список элементов через запятую; левые
  элементы может вписать клиент, правые ставят прокси.
- **Код причины отката**: `no_header` / `fewer_than_n` / `not_ip`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При N = 1 и цепочке, где прокси ставит одно значение, 7 из 7 проверок купона с
  разными подделанными левыми элементами доходят до бек-офиса с одним и тем же адресом гостя.
- **SC-002**: Без настройки для 100 % входов тестовой матрицы бек-офис получает тот же адрес,
  что и до фичи.
- **SC-003**: Во всём журнальном выводе тестов старта и отката — 0 вхождений тестовых адресов
  гостей (адреса из документационных диапазонов) и 0 трейсбеков; на каждый откат — ровно 1
  WARNING-строка.
- **SC-004**: Ссылки в `/robots.txt` и `/sitemap.xml` совпадают с ссылками до фичи во всех
  топологиях матрицы и при всех значениях настройки (0 расхождений по схеме и хосту).
- **SC-005**: Два гостя с разными адресами за одной цепочкой при N = 1 получают разные адреса в
  100 % случаев матрицы.
- **SC-006**: Все прежние тесты сайта (pytest и Playwright-смока) зелёные; поведение
  `/book`, виджета и шаблонов не меняется.

## Assumptions

- Прокси в топологиях (б) и (в) ставят ровно одно значение заголовка — это зафиксировано в
  README выката (вне репо) и конфигах прокси; фича их не меняет.
- Выкат на прод (Lambda) и выбор N там — вне фичи, только с отдельного «да» владельца
  (решение 11.09). До этого прод работает в режиме по умолчанию.
- Бек-офисная половина (`_client_ip` в репозитории aparts) — отдельная спецификация; сайт
  по-прежнему передаёт адрес в исходящем X-Forwarded-For одним значением.
- `api_client.py` уже умеет передавать адрес и не передаёт заголовок, если адрес пуст; фича его
  не меняет.
- Вне фичи: `static/main.js`, шаблоны, `/book`, `e2e/`, конфиг nginx (вне репо), конфиг Caddy (вне репо),
  юниты systemd (вне репо), `wsgi_adapter.py`, `infra/`, `api_client.py`.
- В спеке, тестах и примерах — только адреса из документационных диапазонов (192.0.2.0/24,
  198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32).
