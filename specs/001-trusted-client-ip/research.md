# Research: Доверенный IP гостя из X-Forwarded-For

Все решения согласованы с дирижёром в clarify 2026-09-11 (spec.md → Clarifications). Факты о
библиотеках прочитаны в установленном коде venv `~/venvs/central-aparts-site`, не по памяти.

## R1. Свой разбор, а не werkzeug ProxyFix

**Decision**: собственная функция `_visitor_ip()` в `app.py`, которая вычисляет только адрес для
бек-офиса. ProxyFix не подключается, `request.remote_addr`, схема и хост не меняются.

**Rationale**:
- werkzeug 3.1.8 `ProxyFix.__init__(app, x_for=1, x_proto=1, x_host=0, x_port=0, x_prefix=0)` —
  **`x_proto=1` по умолчанию**: ProxyFix начинает верить X-Forwarded-Proto и переписывает
  `wsgi.url_scheme`. `/robots.txt` и `/sitemap.xml` строятся от `request.url_root` (`app.py`,
  маршруты `robots_txt` и `sitemap_xml`): любая ошибка в доверии к схеме или хосту меняет ссылки
  в них. Если gunicorn окажется открыт напрямую, клиент подменит схему одним заголовком.
- Схема на коробке **уже правильная без ProxyFix**: gunicorn 26.2.0 по умолчанию
  `forwarded_allow_ips = ['127.0.0.1', '::1']` и
  `secure_scheme_headers = {'X-FORWARDED-PROTOCOL': 'ssl', 'X-FORWARDED-PROTO': 'https', 'X-FORWARDED-SSL': 'on'}`
  — от Caddy/nginx на 127.0.0.1 с `X-Forwarded-Proto: https` gunicorn сам ставит
  `wsgi.url_scheme = https`. На Lambda `wsgi_adapter.py` ставит `wsgi.url_scheme = "https"`
  жёстко. Трогать схему незачем.
- `ProxyFix._get_real_value(trusted, value)` возвращает `None`, если значений меньше `trusted`,
  и тогда `REMOTE_ADDR` остаётся как был. На Lambda это первый (подделываемый) элемент
  (`wsgi_adapter.py:57-58`), и откат выбрать нельзя.
- Режим по умолчанию «первый элемент» (решение владельца 1) ProxyFix не выражает, так что свой
  код нужен в любом случае. Два механизма вместо одного — лишняя сложность (конституция VII).
- ProxyFix оборачивает `app.wsgi_app` целиком, включая путь Lambda (`wsgi_adapter` зовёт
  `app.wsgi_app`), а фича Lambda не трогает.

**Alternatives considered**:
- ProxyFix с `x_for=N` и остальными `x_*=0` плюс свой код для режима по умолчанию — отвергнуто:
  два механизма, глобальная подмена `REMOTE_ADDR`, неуправляемый откат.
- ProxyFix по умолчанию — отвергнуто: меняет схему (`x_proto=1`).

## R2. Откат при нехватке элементов — к адресу соединения

**Decision**: при N ≥ 1 и `no_header` / `fewer_than_n` / `not_ip` адрес гостя = адрес соединения
(`request.remote_addr`), а если его нет — пустая строка.

**Rationale**: на коробке адрес соединения — это Caddy/nginx на 127.0.0.1 или локальный клиент
(gunicorn слушает только 127.0.0.1), подделать его извне нельзя. Пустой адрес хуже: бек-офис
посчитает по своему соединению, то есть по выходу сайта, — все такие гости в одном ведре, 429
всем подряд. Самый левый элемент подделывает клиент, и дыра возвращается.

**Ограничение (Lambda)**: `wsgi_adapter.py:57-58` при наличии заголовка ставит `REMOTE_ADDR` =
первый элемент X-Forwarded-For. На Lambda при N ≥ 1 откат из `fewer_than_n` / `not_ip` падает на
подделываемый адрес. Поэтому N на Lambda — вне фичи (spec.md → «Ограничения»).

**Alternatives considered**: пустой адрес; самый левый элемент — отвергнуты по причинам выше.

## R3. Журнал без адресов

**Decision**:
- при импорте `app.py` — одна INFO-строка о режиме: `client_ip_mode mode=default`,
  `client_ip_mode mode=ignore_header` или `client_ip_mode mode=trusted_proxies n=<N>`;
- при неверной настройке — дополнительно одна ERROR-строка
  `client_ip_config_invalid env=TRUSTED_PROXY_COUNT fallback=default` (без значения);
- при откате — одна WARNING-строка на запрос `client_ip_fallback reason=<код> elements=<число>`,
  без `exc_info`, без адресов и без содержимого заголовка.

**Rationale**: неверное N не видно ни по ошибкам, ни по тестам — сигнал нужен, а с кодом и числом
элементов он безопасен. Формат `ключ=значение` — как у соседних строк (`quote apt=…`,
`coupon_check eligible=…`). Модульный `logger` в `app.py` уже на уровне INFO (строка 19,
«Lambda root logger stays WARNING»), поэтому INFO о режиме видна и на Lambda. DEBUG туда не
пишется, поэтому для отката он не подходит.

**Уточнение дирижёра**: не больше одной строки на запрос. Это выполняется устройством:
`_visitor_ip()` вызывается ровно один раз на запрос в каждом из двух маршрутов.

**Число строк при старте**: одна INFO-строка **на процесс**. При `gunicorn -w 2` это две строки
(по одной на воркер), на Lambda — одна на холодный старт. Это ожидаемо и в тестах проверяется
вызовом `_log_client_ip_mode()` напрямую.

**Где строки видны (проверено 2026-09-11 грепом по репозиторию)**: журнал нигде не
настраивается: нет `basicConfig`/`dictConfig`, у gunicorn в юнитах systemd (вне репо) и
`wsgi.py` нет `--log-level`/`--log-config`. Следствия:
- на Lambda среда выполнения ставит обработчик на корневой логгер, а у логгера `app` уровень
  INFO. Видны INFO, WARNING, ERROR;
- на коробке под gunicorn у корневого логгера обработчика нет, срабатывает запасной обработчик
  Python только для WARNING и выше. Видны WARNING `client_ip_fallback` и ERROR
  `client_ip_config_invalid`. INFO `client_ip_mode` в журнал **не попадёт** — ровно как уже
  сегодня не попадают INFO-строки `quote …`. Это существующее свойство коробки, а не свойство
  фичи. Настройка журнала gunicorn — вне фичи (решает дирижёр). Тесты проверяют строки через
  `caplog`, независимо от обработчиков.

**Alternatives considered**: только строка при старте — откаты незаметны; откат на DEBUG — на
Lambda теряется; поднять строку режима до WARNING, чтобы её было видно на коробке, — отвергнуто:
это противоречит ответу clarify (INFO) и засоряет WARNING штатным событием.

## R4. Неверная настройка — режим по умолчанию + ERROR

**Decision**: значение, не подходящее под `^[0-9]+$` после `strip()` (например `abc`, `-1`, `1.5`,
`+1`), → режим по умолчанию и ERROR-строка при старте без значения.

**Rationale**: решение владельца 1 — без явной правильной настройки прод работает как сейчас.
Упавший сайт бронирования — это потерянные деньги (на Lambda — 500 на всём сайте). Опечатку
видно ERROR-строкой при старте, а обязательный эксперимент из README выката (вне репо) после смены
топологии её поймает.

**Alternatives considered**: падать при старте — отвергнуто (доступность); зажимать
отрицательное в 0 — отвергнуто (0 молча отключает заголовок).

## R5. Имя и семантика настройки

**Decision**: `TRUSTED_PROXY_COUNT`; не задана/пусто — режим по умолчанию; `0` — заголовок
игнорируется; `N ≥ 1` — N-й непустой элемент справа. Для коробки (б) и (в) — `1`.

**Rationale**: различает «как сейчас» и «прокси нет» (топология (г)). Имя говорит, что
считается, и не привязано к конкретной библиотеке.

## R6. Проверка элемента как адреса

**Decision**: `ipaddress.ip_address(element)` из стандартной библиотеки; `ValueError` → код
`not_ip`. Проверяется только в режиме N ≥ 1. В режиме по умолчанию — никакой проверки (как
сейчас, FR-002).

**Rationale**: без новых зависимостей. Отбрасывает `unknown`, адрес с портом (`203.0.113.7:443`)
и адрес в скобках (`[2001:db8::1]`) — такие значения прокси, которыми мы управляем, не ставят.
Их появление означает неверное N или чужую ланку, то есть повод для WARNING.

## R7. Как тестировать топологии без сети

**Decision**: Flask test client с `headers={"X-Forwarded-For": …}` и
`environ_base={"REMOTE_ADDR": …}`. Топология (а) дополнительно — через настоящий
`wsgi_adapter.lambda_handler` синтетическим событием Function URL (без AWS SDK и сети).
Режим — `monkeypatch.setattr(Config, "TRUSTED_PROXY_COUNT", …)`.

**Полная матрица FR-011** — ожидаемый адрес для бек-офиса (одинаков для обоих маршрутов);
`+ код` — плюс ровно одна WARNING `client_ip_fallback` с этим кодом:

| Топология | X-Forwarded-For на входе | REMOTE_ADDR | не задана / неверная | N = 0 | N = 1 | N = 2 |
|---|---|---|---|---|---|---|
| (а) CloudFront → Lambda | `198.51.100.23, 203.0.113.7` | `198.51.100.23` (так ставит `wsgi_adapter`) | `198.51.100.23` | `198.51.100.23` ¹ | `203.0.113.7` | `198.51.100.23` ² |
| (б) Caddy → gunicorn | `203.0.113.7` | `127.0.0.1` | `203.0.113.7` | `127.0.0.1` ³ | `203.0.113.7` | `127.0.0.1` + `fewer_than_n` |
| (в) Caddy → nginx → gunicorn | `203.0.113.7` | `127.0.0.1` | `203.0.113.7` | `127.0.0.1` ³ | `203.0.113.7` | `127.0.0.1` + `fewer_than_n` |
| (г) напрямую, подделка | `198.51.100.23` | `192.0.2.50` | `198.51.100.23` | `192.0.2.50` | `198.51.100.23` ⁴ | `192.0.2.50` + `fewer_than_n` |
| (г) напрямую, без заголовка | — | `192.0.2.50` | `192.0.2.50` | `192.0.2.50` | `192.0.2.50` + `no_header` | `192.0.2.50` + `no_header` |

¹ На Lambda «адрес соединения» — первый элемент (`wsgi_adapter.py:57-58`), поэтому N = 0 там
подделываем. Это иллюстрация ограничения, а не рекомендация.
² N = 2 для (а) неверно: второй справа — присланное клиентом.
³ N = 0 за прокси неверно: все гости в одном ведре (адрес прокси).
⁴ N = 1 для (г) неверно: без прокси самый правый элемент — присланное клиентом.

Строка (а) показывает **гипотезу** о CloudFront (дописывает справа). Тест проверяет разбор при
такой форме заголовка, но не доказывает, что CloudFront так делает: это не измерено. Неверные
для топологии значения N (¹–⁴) в матрице нужны, чтобы тесты закрепили механику, а README —
показал цену ошибки.

## R8. Что НЕ проверено и остаётся вне фичи

- Форма X-Forwarded-For на цепочке CloudFront → Lambda Function URL (дописывает ли кто-то ещё) —
  не измерено; нужно для выбора N на Lambda, решение владельца.
- Живой эксперимент на коробке «7 запросов с подделкой → 5 × 422, 2 × 429» — из
  README выката (вне репо), делается при установке (Task 2.1/2.2), не в этой фиче.
