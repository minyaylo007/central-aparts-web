# Feature Specification: Бережные обращения сайта к бек-офису

**Feature Branch**: нет (Spec Kit без git-расширения; работа в worktree, в `master` — перемоткой; папка `specs/002-bounded-backoffice-calls/`)

**Created**: 2026-09-11

**Status**: Clarified

**Input**: User description: "Сайт не должен перегрузить бек-офис, когда тот переедет с Lambda на машину (2 процесса × 4 потока и SQLite: ~100 котировок/с займут все слоты, встанет админка у живых сотрудников). Два механизма, оба управляются настройками окружения и ПО УМОЛЧАНИЮ ВЫКЛЮЧЕНЫ (поведение как сейчас): (1) короткий кеш котировки /api/quote в сайте для ответов БЕЗ купонного телефона; (2) потолок одновременных обращений из одного процесса сайта к бек-офису + понятная гостю реакция при переполнении вместо зависания."

## Контекст

Сайт не хранит данных: каждая страница, котировка, проверка купона и бронь — обращение к
публичному API бек-офиса. Каталог, квартира, занятость и цены по дням уже кешируются в процессе
сайта (60 / 120 / 30 / 900 с), поэтому страницы бек-офис почти не нагружают. При сбое бек-офиса
(любое исключение, в том числе ответ 503) для них отдаётся устаревшее значение: записи из этого
кеша не удаляются, поэтому устаревшее живёт до перезапуска процесса (сверено по `api_client.py`,
11.09). Котировка (`/api/quote/<apt_id>`) не кешируется совсем: цена в виджете — это сумма
будущего счёта в Монобанке, «сервер — единственная правда о сумме» (CLAUDE.md §7).

Бек-офис переезжает с Lambda на машину, где его публичную часть обслуживают 2 процесса × 4 потока
поверх SQLite. Замер 11.09 (deploy/README.md, «Замір із затримкою бек-офісу»; задержка
бек-офиса 350 мс, 50 одновременных) показал: котировка упирается в число потоков сайта — p95
3,9 с при `-w 2 --threads 4` и 699 мс при `-w 3 --threads 12`, на которые сервис сайта
переходит. 36 потоков сайта при 350 мс на ответ — это до ~100 котировок/с в бек-офис; по словам
дирижёра бек-офиса (11.09), столько займёт все его слоты, и встанет админка у сотрудников,
которые в ней работают. Бек-офис попросил: кеш котировки 30–60 с по ключу «квартира + даты +
гости», потолок параллельных обращений (например 8) и таймаут. Ёмкость бек-офиса он измерил на
копии боевых данных (как в проде: gunicorn 2 × 4 gthread, SQLite, `127.0.0.1:8008`; сведения
дирижёра, 11.09): только котировки, 50 одновременных × 60 с — 125,8/с, p95 515 мс, 5xx 0;
50 котировок + 5 админов на дашборде — p95 котировки 642 мс, дашборда 583 мс, 5xx 0, «database is
locked» 0 (котировка ничего не пишет). **Бюджет — до 50 одновременных котировок на весь сайт** без
ущерба админке; свой лимит на `/api/public` бек-офис поставит позже, выше 50. Сервис сайта при
`-w 3 --threads 12` даёт не больше 36 одновременных обращений — меньше бюджета, поэтому потолок
при этих флагах не нужен; оба механизма по умолчанию выключены, кеш котировки — запас.

После переезда бек-офиса сайт будет ходить к нему напрямую — `BACKOFFICE_URL=http://127.0.0.1:8008`
(в обход Caddy: иначе Caddy склеит адреса гостей); до переезда — `https://cv.central-aparts.store`
(Lambda). Защищаем именно локальный бек-офис: его ёмкость меньше. Бек-офис может поставить у себя
лимит на `/api/public`; код и тело ответа при переполнении он сообщит (сведения дирижёра, 11.09).

**Режим техработ бек-офиса** (по коду бек-офиса, `backend/app.py`, `_cutover_gate`, как есть
11.09 — сведения дирижёра): включается `MAINTENANCE=1`, читается на каждый запрос; закрывает
**все** `/api/public/*` — и чтения (каталог, квартира, занятость, цены, котировка, проверка купона),
и бронь; открыты `/health` и статика. Ответ: HTTP 503, `Retry-After: 300` (секунды),
`Cache-Control: no-store`, тело — HTML-страница техработ; позже тело станет JSON
`{"error": "maintenance", "retry_after": 300}` с теми же кодом и заголовками. Окно — около 5 минут
(план — 04:30 по Киеву), дата не назначена. Сегодня сайт на 503 брони показывает общую ошибку
«Не вдалося створити платіж…», на 503 котировки и проверки купона — то же, что при любом сбое.

Фича даёт сайту два независимых рычага, оба выключенных по умолчанию:

1. **Кеш котировки без купона** — одинаковые запросы котировки (одна квартира, те же даты и
   гости, без купонного телефона) в пределах короткого срока отвечаются из памяти процесса
   сайта, без обращения к бек-офису.
2. **Потолок одновременных обращений** — процесс сайта держит не больше N обращений к
   бек-офису одновременно; лишние ждут свободного места ограниченное время и, не дождавшись,
   получают быстрый понятный отказ вместо того, чтобы висеть до таймаута.

И одну реакцию, которая действует всегда, без настройки: **понятный гостю ответ, когда бек-офис
сам говорит «временно недоступен»** (свой лимит или техработы).

## Clarifications

### Session 2026-09-11

Вопросы задавались дирижёру «🌐 Сайт бронирования — дирижёр» одним сообщением (канал
асинхронный); все пять ответов — по рекомендации спецификатора, с уточнениями дирижёра.

- Q: Что входит в ключ кеша котировки, какой срок, что не кешировать, сбрасывать ли после
  брони? → A: Ключ — квартира + заезд + выезд + гости (язык не входит: сайт не передаёт его в
  котировку; plan MUST проверить по коду, что ответ не зависит ни от чего сверх этого, и при
  зависимости ключ расширять, не сужать). Кешируются только успешные ответы без купонного
  телефона; котировка с `coupon_phone`, 400/404, ошибки и отказы — никогда. Срок —
  `QUOTE_CACHE_TTL`, при включении 30 с. Просроченное не отдаётся никогда, в том числе при сбое
  бек-офиса. Сброса после `/book` нет. Граница — 2000 записей на процесс (FR-001–FR-006).
- Q: Потолок на процесс или на весь сайт, трогаем ли таймаут? → A: На процесс,
  `BACKOFFICE_MAX_CONCURRENT` = N; правило «сайт = процессы × N», а при бюджете бек-офиса на весь
  сайт — N = бюджет / процессы с округлением вниз, в `deploy/README.md` рядом с таблицей замера.
  Таймауты обращений не меняются: чтения 10 с, бронь 30 с (FR-007, FR-017).
- Q: Сколько ждёт гость при занятом потолке и что получает? → A: Ждёт место до
  `BACKOFFICE_SLOT_WAIT` (по умолчанию 2 с); не дождавшись — без обращения к бек-офису:
  JSON-ручки (котировка, занятость, цены, проверка купона) — 503 `{"error": "busy"}` +
  `Retry-After: 5`; страницы — прежнее значение из кеша, без него — как при сбое бек-офиса сейчас.
  Виджет на 503 котировки ведёт себя так же, как на сегодняшний неуспешный ответ (`static/main.js`
  проверяет только «не ок», код ошибки и тело не читает — сверено при clarify, plan
  перепроверяет); `main.js` не меняется (FR-008, FR-011).
- Q: Касается ли потолок брони и страницы подтверждения? → A: Нет: `/book` (создание брони) и
  страница подтверждения после оплаты идут в обход потолка — денежный путь; ответы из кешей
  места не занимают (FR-009, FR-010).
- Q: Что пишем в журнал и как доказываем эффект? → A: При старте INFO о режимах; на неверную
  настройку одна ERROR с именем, без значения, механизм выключен; в строке `quote` —
  `cache=hit|miss|off`; каждый отказ — WARNING `backoffice_busy` с видом обращения и временем
  ожидания, не чаще 1 строки в секунду на процесс, с числом подавленных; без адресов, телефонов,
  дат и номеров броней — тест на это, как в 001; периодической сводки нет. Эффект — pytest
  (пик одновременных ≤ N, отказ ≤ W + 0,5 с) и замер oha до/после на подмене; границы
  расширены на маленькую правку `e2e/fake_transport.py` — счётчик обращений и пик одновременных
  в `/__fake__/state`, выключено по умолчанию, покрыто `e2e/test_fake_transport.py`, смока не
  меняется (FR-013–FR-015, FR-018, FR-021).
- Дополнение дирижёра: после переезда `BACKOFFICE_URL=http://127.0.0.1:8008`; механизмы не
  зависят от адреса бек-офиса (FR-019).
- Дополнение дирижёра (режим техработ бек-офиса, три сообщения 11.09): ответ бек-офиса 503/429
  распознаётся только по коду и `Retry-After`, тело не разбирается (FR-020). JSON-ручки — как
  отказ потолка, но `Retry-After` — из ответа бек-офиса (FR-020). `/book` — отдельная строка
  «бронювання тимчасово недоступне, спробуйте за N хвилин» из `translations.py` (ua и en), N из
  `Retry-After` с округлением вверх до минут, без него — без числа; даты и гости гостя
  сохраняются; `/book` по-прежнему мимо потолка сайта (FR-022). Проверка купона — generic-ответ
  без сигнала для перебора (FR-023). Страницы в окне держатся на устаревшем значении кеша —
  сверено по коду, отдельного требования не нужно (FR-024). В журнале техработы/«недоступен»
  отличимы от `busy` и от прочего сбоя (FR-020). Тесты — подменная сессия с 503 +
  `Retry-After` + HTML на всех путях (FR-018). `main.js` не меняется.
- Решения дирижёра по спорному: купон — прежняя общая строка `coupon_error` (без правки
  `main.js`); при техработах `/book` возвращает даты + гостей + флаг пересчёта, как при
  `too_many_holds`; реакция на 429/503 «всегда, без настройки» принята как отступление в FR-016.
  Смена `BACKOFFICE_URL` на `127.0.0.1:8008` требует перезапуска сервиса сайта, а перезапуск
  обнуляет кеш: в окне техработ не перезапускать; переключение и перезапуск — только когда
  бек-офис на 8008 уже отвечает без техработ (сигнал дирижёра бек-офиса); сразу после
  перезапуска — прогреть главную и все квартиры одним GET (FR-017).
- Цифры ёмкости бек-офиса (дирижёр, после plan): бюджет — 50 одновременных котировок на весь сайт.
  По правилу Q2 N = ⌊50 / 3⌋ = 16 ≥ 12 потоков на процесс — при `-w 3 --threads 12` потолок не
  срабатывает; в README — расчёт «потолок нужен, когда процессы × потоки > 50»; механизм остаётся
  выключенным по умолчанию (FR-017).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Без настроек ничего не меняется (Priority: P1)

Владелец выкатывает код, не задавая новых настроек (так будет и на Lambda, и на машине до
отдельного выката с цифрами бек-офиса). Каждая котировка по-прежнему доходит до бек-офиса,
обращения к бек-офису не ограничиваются, гость видит всё то же, что сейчас — кроме случая, когда
бек-офис сам ответил «временно недоступен» (US5).

**Why this priority**: решение главного дирижёра — по умолчанию поведение как сейчас. Выкат
кода не должен сам по себе ни менять цены на экране, ни отказывать гостям.

**Independent Test**: весь прежний набор тестов и смока без новых настроек; отдельный тест —
N одинаковых котировок без купона дают N обращений к подменному бек-офису.

**Acceptance Scenarios**:

1. **Given** обе настройки не заданы, **When** гость дважды подряд запрашивает котировку одной
   квартиры на те же даты и гостей, **Then** бек-офис получает два запроса котировки.
2. **Given** обе настройки не заданы и бек-офис отвечает медленно, **When** приходит 50
   одновременных запросов, **Then** все 50 уходят в бек-офис без ожидания в сайте и без отказов
   сайта (как сейчас).
3. **Given** `QUOTE_CACHE_TTL` и `BACKOFFICE_MAX_CONCURRENT` заданы пустой строкой или 0,
   **When** гость запрашивает котировку, **Then** поведение то же, что при незаданных настройках.

### User Story 2 - Повторные котировки без купона не долетают до бек-офиса (Priority: P1)

Владелец включает кеш котировки со сроком T секунд (при включении — 30 с). Много гостей смотрят
одну квартиру на популярные даты (выходные, праздник), виджет и бейджи поиска на главной шлют
одинаковые котировки. В течение T секунд после первого ответа одинаковые котировки без купонного
телефона сайт отдаёт из памяти; бек-офис видит одну котировку на ключ на процесс сайта за срок.

**Why this priority**: котировка — единственное горячее обращение без кеша; поток бейджей на
главной и перевыборы дат в виджете дают много одинаковых запросов. Это главный рычаг снижения
нагрузки, о котором просил бек-офис.

**Independent Test**: при включённом кеше серия одинаковых котировок без купона в пределах
срока — одно обращение к подменному бек-офису; после срока — снова обращение.

**Acceptance Scenarios**:

1. **Given** кеш включён со сроком T, **When** 100 одинаковых котировок без купона приходят в
   один процесс сайта в течение T, **Then** бек-офис получает 1 запрос котировки, а все 100
   гостей получают тот же ответ, что дал бек-офис.
2. **Given** кеш включён, **When** котировки отличаются квартирой, датой заезда, датой выезда
   или числом гостей, **Then** каждая отличающаяся котировка идёт в бек-офис отдельно.
3. **Given** кеш включён, **When** гость запрашивает котировку с купонным телефоном, **Then**
   запрос всегда уходит в бек-офис (вместе с адресом гостя для лимита перебора купонов), ответ
   не попадает в кеш и не берётся из кеша — ни для этого, ни для другого гостя.
4. **Given** кеш включён и бек-офис ответил «неверный ввод» (400/404), ошибкой или «временно
   недоступен», **When** тот же запрос повторяется, **Then** он снова уходит в бек-офис.
5. **Given** кеш включён и срок записи истёк, **When** приходит та же котировка, **Then** она
   уходит в бек-офис, и ответ бек-офиса заменяет запись; если бек-офис при этом не ответил,
   гость получает ошибку, а не просроченную котировку.

### User Story 3 - Всплеск не забивает бек-офис, гость не висит (Priority: P1)

Владелец включает потолок N обращений на процесс. Приходит всплеск (реклама, бот, 50
одновременных котировок с разными датами — кеш не помогает). Каждый процесс сайта держит в
бек-офисе не больше N обращений одновременно, поэтому сайт целиком — не больше «число процессов
× N»; остальные ждут свободного места не дольше W и, не дождавшись, получают быстрый отказ.
Админка бек-офиса у сотрудников продолжает работать. Бронь идёт мимо потолка.

**Why this priority**: кеш не спасает от разных ключей; только потолок гарантирует бек-офису
верхнюю границу нагрузки от сайта. Без понятного отказа гость видел бы вечно крутящийся виджет.

**Independent Test**: подменный бек-офис с задержкой и счётчиком одновременных обращений;
параллельная нагрузка на один процесс сайта; максимум одновременных обращений не превышает N,
лишние запросы получают отказ не позже W + 0,5 с.

**Acceptance Scenarios**:

1. **Given** потолок N и бек-офис с задержкой, **When** в один процесс приходит больше N
   одновременных обращений, **Then** одновременно в бек-офисе не больше N из них.
2. **Given** потолок N, все места заняты и не освобождаются дольше W, **When** гость
   запрашивает котировку, **Then** сайт отвечает ему не позже чем через W + 0,5 с ответом 503
   `{"error": "busy"}` с `Retry-After: 5`, не обращаясь к бек-офису; виджет оставляет на экране
   предварительную оценку, как при любом сбое котировки сейчас.
3. **Given** потолок N и место освобождается раньше W, **When** ожидающий запрос получает
   место, **Then** он обслуживается как обычно, гость получает обычный ответ.
4. **Given** потолок включён и кеш котировки включён, **When** котировка отдаётся из кеша,
   **Then** она не занимает место под потолком и не ждёт.
5. **Given** потолок включён, все места заняты, **When** гость открывает главную или страницу
   квартиры, данные которых есть в кеше каталога, **Then** страница отдаётся из кеша без ожидания;
   если кеш просрочен и места нет W секунд — отдаётся прежнее значение (как при сбое бек-офиса
   сейчас), а без прежнего значения — поведение как при сбое бек-офиса сейчас.
6. **Given** потолок включён и все места заняты, **When** гость отправляет бронь (`/book`) или
   открывает страницу подтверждения после оплаты, **Then** обращение идёт в бек-офис сразу, не
   дожидаясь места и не занимая его.

### User Story 4 - Эксплуатация видит, как работают рычаги (Priority: P2)

Владелец или дежурная сессия по журналу понимают, включены ли кеш и потолок и с какими
значениями, сколько котировок отдано из кеша, сколько обращений отклонено потолком и когда
бек-офис отвечал «временно недоступен». Адресов гостей, телефонов, дат и номеров броней в
журнале нет. В документации выката объяснено, какие значения ставить на машине и почему, и как
проверить эффект замером на подмене до включения.

**Why this priority**: включение — отдельный выкат с цифрами бек-офиса; без счётчиков нельзя ни
подобрать N и T, ни заметить, что потолок режет живых гостей.

**Independent Test**: запуск с разными значениями настроек; проверяются стартовые записи о режиме,
записи об отказах и о «временно недоступен», отметка кеша в строке котировки; во всём журнальном
выводе тестов нет тестовых адресов, телефонов, дат и номеров броней.

**Acceptance Scenarios**:

1. **Given** любые значения настроек, **When** процесс сайта стартует, **Then** логгер приложения
   выдаёт по одной INFO-записи о режиме кеша котировки и режиме потолка (значения — числа, без
   адресов).
2. **Given** настройка задана неверно (не число, отрицательное), **When** сайт стартует, **Then**
   этот механизм выключен, а в журнале одна ERROR-строка с именем настройки, без её значения.
3. **Given** потолок отклонил 50 обращений за одну секунду в одном процессе, **When** смотрят
   журнал, **Then** там не больше двух WARNING-строк `backoffice_busy` за эту секунду: вид
   обращения, время ожидания и число подавленных строк — без адреса гостя, телефона, дат и
   параметров запроса гостя.
4. **Given** котировка отдана, **When** смотрят её строку `quote`, **Then** в ней `cache=hit`,
   `cache=miss` или `cache=off`.
5. **Given** бек-офис отвечает «временно недоступен», **When** смотрят журнал, **Then** там
   WARNING-строки `backoffice_unavailable` с кодом ответа, `Retry-After` и видом обращения,
   отличимые от `backoffice_busy` и от прочих ошибок бек-офиса.
6. **Given** документация выката, **When** владелец включает механизмы на машине, **Then** он
   находит в `deploy/README.md` и `deploy/site.env.example` смысл каждой настройки, правило
   «N = бюджет сайта / процессы, вниз», рекомендуемые значения и процедуру замера на подмене.

### User Story 5 - Техработы бек-офиса: гость понимает, что происходит (Priority: P1)

Бек-офис на ~5 минут включает режим техработ: все его публичные ручки отвечают 503 с
`Retry-After: 300`. Гость, который в это время смотрит сайт, видит страницы из кеша сайта; его
котировка и проверка купона получают быстрый понятный отказ; нажав «Оплатити», он возвращается на
страницу квартиры со своими датами и гостями и читает «Бронювання тимчасово недоступне,
спробуйте за 5 хвилин», а не «Не вдалося створити платіж».

**Why this priority**: окно техработ — плановое событие переезда; общая ошибка на брони выглядит
как поломка и уводит гостя. Действует без настроек: без неё переезд бек-офиса бьёт по гостям.

**Independent Test**: подменная сессия бек-офиса отвечает на все пути 503 + `Retry-After: 300` +
HTML-тело; проверяются главная и квартира (с устаревшим кешем и с холодным), занятость, цены,
котировка, проверка купона, бронь и страница подтверждения.

**Acceptance Scenarios**:

1. **Given** бек-офис отвечает 503 + `Retry-After: 300` + HTML, **When** гость отправляет бронь,
   **Then** он возвращается на страницу квартиры с теми же датами и числом гостей и видит
   сообщение «бронювання тимчасово недоступне, спробуйте за 5 хвилин» на своём языке (ua/en);
   бронь не повторяется сайтом.
2. **Given** бек-офис отвечает 503 без `Retry-After` (или с нечисловым значением), **When** гость
   отправляет бронь, **Then** он видит то же сообщение без числа минут («спробуйте трохи пізніше»).
3. **Given** бек-офис отвечает 503 + `Retry-After: 300`, **When** гость запрашивает котировку,
   занятость или цены, **Then** сайт отвечает 503 `{"error": "busy"}` с `Retry-After: 300`, виджет
   оставляет предварительную оценку.
4. **Given** бек-офис отвечает 503, **When** гость проверяет купон, **Then** сайт отвечает тем же
   503 `{"error": "busy"}`, а виджет показывает прежнее сообщение «Не вдалося перевірити купон —
   спробуйте ще раз» — одинаковое для любого телефона, без сигнала для перебора.
5. **Given** бек-офис отвечает 503 и процесс сайта уже показывал главную и квартиру, **When**
   гость открывает их, **Then** страницы отдаются из устаревшего кеша сайта.
6. **Given** бек-офис отвечает 503 и кеш процесса пуст (процесс стартовал в окне), **When** гость
   открывает главную или квартиру, **Then** поведение как при сбое бек-офиса сейчас (главная без
   карточек, квартира — страница ошибки).
7. **Given** бек-офис отвечает 503 и тело — JSON `{"error": "maintenance", "retry_after": 300}`
   вместо HTML, **When** повторяются сценарии 1–6, **Then** результат тот же.

### Edge Cases

- Одинаковые котировки приходят одновременно, пока записи в кеше ещё нет: каждая может уйти в
  бек-офис (объединения одновременных промахов фича не обещает); их число ограничено потолком,
  если он включён.
- Цена квартиры меняется в админке, пока в кеше лежит котировка: гость до T секунд видит прежнюю
  сумму; бронь пересчитывается бек-офисом и в Монобанк уходит его сумма (см. «Ограничения»).
- Даты забронировали, пока котировка лежит в кеше: гость до T секунд видит котировку на уже
  занятые даты; бронь бек-офис отклонит (409 «даты заняты», как сейчас при гонке). Сброса кеша
  после брони нет.
- Число гостей приходит в разных записях (`2` и `02`): это разные ключи кеша; вреда нет, кроме
  лишнего обращения.
- Полночь: котировка с заездом «сегодня», положенная в кеш незадолго до полуночи, живёт до T
  секунд после неё, хотя бек-офис уже ответил бы «неверный ввод»; бронь бек-офис проверит сам
  (research.md R2).
- Много разных ключей (перебор дат ботом): кеш котировки в процессе ограничен 2000 записей; при
  переполнении старые вытесняются, память процесса не растёт.
- Все процессы сервиса читают одно окружение при старте, поэтому настройки у них одинаковые;
  изменение настроек действует только после перезапуска.
- Бек-офис отвечает дольше W: запрос, уже получивший место, ждёт ответа до прежнего таймаута
  обращения (10 с чтения); W ограничивает только ожидание места.
- Потолок включён на Lambda: там один запрос на экземпляр, потолок ни на что не влияет; кеш — в
  памяти экземпляра. Включать на Lambda фича не предлагает.
- Под потолком стоят и промахи кеша каталога, и котировки, и проверки купона: всплеск котировок
  может задержать промах кеша каталога; страницы от этого защищает отдача прежнего значения.
- Бронь идёт мимо потолка, поэтому в бек-офисе одновременно может быть N + число броней в
  процессе; брони — единицы в час.
- `Retry-After` в виде даты HTTP, отрицательный, нулевой или больше 3600 с: считается
  отсутствующим — сообщение брони без числа, JSON-ручки отдают `Retry-After: 5`.
- Число минут: `ceil(секунды / 60)`, 1–60; форма слова по правилам языка (ua: 1 хвилину,
  2–4 хвилини, 5–20 хвилин, 21 хвилину…; en: 1 minute, N minutes).
- 503 от бек-офиса на Lambda (сбой самой Lambda, а не техработы) тоже распознаётся как «временно
  недоступен»: для гостя это честнее общей ошибки, повторов сайт не делает.
- Проверка брони на странице подтверждения в окне: как сейчас при сбое (страница без данных брони).

## Ограничения

- **Кеш ослабляет «цена на экране = счёт» на срок T.** Пока котировка лежит в кеше, изменение
  цены в админке или занятость дат гость увидит с опозданием до T секунд. Сумму счёта всегда
  считает бек-офис при брони, поэтому деньги не расходятся со счётом — расходится только
  показанная до брони цена в течение T. Поэтому T короткий (30 с) и задаётся явно при включении.
- Кеш и потолок — на процесс сайта, а не на весь сайт: при `-w 3` бек-офис видит до 3 промахов
  на ключ за срок и до 3 × N одновременных обращений (плюс брони). Общий для процессов счётчик
  потребовал бы внешнего хранилища или межпроцессной блокировки — вне фичи.
- Значения для включения (T, N, W) считаются от бюджета бек-офиса (50 одновременных котировок на
  сайт); включение на машине — отдельный выкат, вне фичи.
- **Реакция на «временно недоступен» не выключается настройкой.** Она меняет только то, что
  гость видит при 429/503 от бек-офиса (сегодня — общая ошибка); логика оплаты, форма брони и
  `main.js` не меняются.
- Процесс, стартовавший внутри окна техработ, не имеет устаревшего кеша: главная без карточек,
  квартира — страница ошибки, как при любом сбое сегодня. Шаблоны фича не меняет; перезапуск
  сервиса сайта в окне техработ бек-офиса не делать (записать в `deploy/README.md`).
- Настройки и `BACKOFFICE_URL` читаются при старте, поэтому переключение на `127.0.0.1:8008`
  требует перезапуска сервиса сайта, который обнуляет все кеши процесса. Переключать — только
  когда бек-офис на 8008 уже отвечает без техработ (сигнал дирижёра бек-офиса), и сразу прогревать
  кеш одним GET главной и каждой квартиры.
- Точная формулировка для проверки купона («тимчасово недоступно») без правки `main.js`
  невозможна: виджет показывает свою строку `coupon_error` на любой неуспешный ответ. Фича
  оставляет её — она generic и не даёт сигнала для перебора.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Кеш котировки MUST управляться настройкой окружения `QUOTE_CACHE_TTL` — срок жизни
  записи в секундах, — которая читается один раз при старте в `config.py` по образцу остальных
  полей класса `Config`. Не задана, пусто или 0 — кеш выключен, каждая котировка идёт в бек-офис,
  как сейчас. Рекомендуемое значение при включении — 30.
- **FR-002**: При включённом кеше сайт MUST отдавать котировку из памяти процесса, если в течение
  последних T секунд этот же процесс получил от бек-офиса успешный ответ на котировку с тем же
  ключом; ключ — квартира, дата заезда, дата выезда, число гостей в том виде, в каком они
  уходят в бек-офис, плюс всё, от чего, по проверке в plan, зависит ответ бек-офиса на котировку
  без купона (ключ можно расширить, но не сузить).
- **FR-003**: Котировка с непустым купонным телефоном MUST NOT браться из кеша и MUST NOT
  попадать в кеш — ни ответ, ни его часть; она всегда уходит в бек-офис с адресом гостя, как
  сейчас.
- **FR-004**: В кеш MUST попадать только успешные ответы бек-офиса на котировку; ответы
  «неверный ввод» (400/404), ошибки, отказы потолка и ответы «временно недоступен» (FR-020) MUST
  NOT кешироваться.
- **FR-005**: Ответ из кеша MUST совпадать с ответом бек-офиса, по которому он сохранён (те же
  поля и значения); кеш MUST NOT отдавать просроченную запись — ни в обычном режиме, ни при
  сбое бек-офиса.
- **FR-006**: Число записей кеша котировки в одном процессе MUST быть не больше 2000; при
  достижении границы новые записи вытесняют старые, память процесса не растёт без предела.
- **FR-007**: Потолок MUST управляться настройкой окружения `BACKOFFICE_MAX_CONCURRENT` (N) —
  наибольшее число одновременных обращений одного процесса сайта к бек-офису; читается один раз
  при старте. Не задана, пусто или 0 — потолка нет, как сейчас. Таймауты обращений MUST
  остаться прежними (чтения 10 с, бронь 30 с).
- **FR-008**: При включённом потолке обращение, для которого нет свободного места, MUST ждать
  место не дольше `BACKOFFICE_SLOT_WAIT` секунд (W; не задана или пусто — 2); не дождавшись, MUST
  завершиться отказом «сервис занят» без обращения к бек-офису.
- **FR-009**: Потолок MUST охватывать все обращения процесса к бек-офису, которые реально идут по
  сети — каталог, квартира, занятость, цены, котировка, проверка купона, — кроме исключённых по
  FR-010. Ответы из кешей сайта (каталог, квартира, занятость, цены, котировка) MUST NOT занимать
  место и ждать.
- **FR-010**: Создание брони (`/book`) и получение брони для страницы подтверждения после оплаты
  MUST идти в бек-офис в обход потолка: не ждать места и не занимать его.
- **FR-011**: Отказ по потолку MUST доходить до гостя тем же путём, что и сбой бек-офиса сейчас,
  только быстро: котировка, занятость, цены, проверка купона — ответ 503 с телом
  `{"error": "busy"}` и заголовком `Retry-After: 5` (виджет оставляет предварительную оценку и
  показывает прежнее сообщение об ошибке купона); главная и страница квартиры — прежнее значение
  из кеша, а без него — поведение как при сбое бек-офиса сейчас.
- **FR-012**: Неверное значение любой из новых настроек (не число, отрицательное) MUST
  выключать соответствующий механизм (для `BACKOFFICE_SLOT_WAIT` — значение по умолчанию 2) и
  давать при старте одну ERROR-строку с именем настройки, без её значения; сайт MUST стартовать.
- **FR-013**: При старте каждого процесса сайт MUST выдавать в логгер приложения по одной
  INFO-записи о режиме кеша котировки (выключен / срок T, граница записей) и режиме потолка
  (выключен / N, W).
- **FR-014**: Отказ по потолку MUST давать WARNING-запись `backoffice_busy` с видом обращения
  (котировка, каталог и т. п.) и временем ожидания — не чаще одной строки в секунду на процесс,
  следующая строка сообщает число подавленных. Запись MUST NOT содержать адрес гостя, телефон,
  даты, номер брони и содержимое заголовков гостя.
- **FR-015**: Существующая INFO-строка `quote` MUST показывать `cache=hit`, `cache=miss` или
  `cache=off`. Никакая журнальная запись фичи MUST NOT содержать адрес гостя, купонный телефон
  (ни целиком, ни частично), номер брони; новые записи фичи (FR-012–FR-014, FR-020, FR-022) MUST
  NOT содержать дат и тела ответа бек-офиса.
- **FR-016**: При выключенных механизмах кеша и потолка поведение сайта (число и порядок обращений
  к бек-офису, ответы гостю, таймауты) MUST совпадать с поведением до фичи во всех случаях, кроме
  ответа бек-офиса «временно недоступен» (FR-020, FR-022, FR-023), реакция на который действует
  всегда. `static/main.js`, шаблоны, расчёт сбора, форма брони и логика оплаты MUST NOT меняться.
- **FR-017**: `deploy/README.md` (рядом с таблицей замера) и `deploy/site.env.example` MUST
  описывать `QUOTE_CACHE_TTL`, `BACKOFFICE_MAX_CONCURRENT`, `BACKOFFICE_SLOT_WAIT`: смысл,
  «выключено» по умолчанию, правило «сайт = процессы × N; N = бюджет бек-офиса на сайт /
  процессы, с округлением вниз», брони мимо потолка, ограничение «цена на экране может отставать
  до T», расчёт для машины по цифрам бек-офиса (бюджет 50 на сайт: при `-w 3 --threads 12` — не
  больше 36 одновременных, потолок не нужен; нужен, когда процессы × потоки > 50, тогда
  N = ⌊50 / процессы⌋) и рекомендуемые T = 30, W = 2,
  процедуру замера эффекта на подмене (FR-021), а также поведение сайта в окне техработ
  бек-офиса и правило перезапуска: в окне техработ сервис сайта не перезапускать; смена
  `BACKOFFICE_URL` на `http://127.0.0.1:8008` и перезапуск — только когда бек-офис на 8008 уже
  отвечает без техработ (сигнал дирижёра бек-офиса); сразу после перезапуска — прогрев главной и
  всех квартир одним GET.
- **FR-018**: Тесты MUST покрывать: выключенное состояние (FR-016); попадание и промах кеша, срок,
  все составляющие ключа; купонный телефон мимо кеша (FR-003); некеширование 400/404, ошибок и
  «временно недоступен» (FR-004); отказ просроченной записи при сбое (FR-005); границу записей
  (FR-006); потолок — максимум одновременных обращений не выше N под параллельной нагрузкой и
  отказ не позже W + 0,5 с (FR-007, FR-008); обход потолка ответами из кеша и бронью (FR-009,
  FR-010); ответы гостю при отказе (FR-011); неверные настройки (FR-012); подменную сессию
  бек-офиса с 503 + `Retry-After: 300` + HTML-телом (и с JSON-телом) на всех путях US5 — главная и
  квартира с устаревшим и с пустым кешем, занятость, цены, котировка, проверка купона, бронь,
  страница подтверждения (FR-020, FR-022–FR-024); отсутствие тестовых адресов, телефонов, дат и
  номеров броней в журнальном выводе (FR-014, FR-015).
- **FR-019**: Кеш, потолок и ожидание MUST работать одинаково при любом `BACKOFFICE_URL` —
  `https://cv.central-aparts.store` (Lambda) и `http://127.0.0.1:8008` (бек-офис на машине);
  значения настроек не зависят от адреса бек-офиса.
- **FR-020**: Ответ бек-офиса с кодом 429 или 503 на любом обращении MUST распознаваться как
  «временно недоступен» только по коду и заголовку `Retry-After`; тело (HTML сейчас, JSON позже)
  MUST NOT разбираться. На таком ответе сайт MUST NOT повторять обращение и MUST NOT кешировать
  ответ. Котировка, занятость, цены, проверка купона MUST отвечать гостю 503 `{"error": "busy"}` с
  `Retry-After`, равным значению бек-офиса, если это целое число секунд от 1 до 3600, иначе 5.
  Каждое такое событие MUST давать WARNING-запись `backoffice_unavailable` с кодом ответа,
  `Retry-After` (число или `none`) и видом обращения — не чаще одной строки в секунду на
  процесс, со счётом подавленных; запись отличима от `backoffice_busy` и от прочих ошибок
  бек-офиса и не содержит данных гостя.
- **FR-021**: Подменный бек-офис для замера (`e2e/fake_transport.py`) MUST уметь считать число
  обращений и пик одновременных обращений и отдавать их в `/__fake__/state` процесса смоки
  (`e2e/fake_wsgi.py`); по умолчанию счёт выключен, смока и CI не меняются; покрыто
  `e2e/test_fake_transport.py`.
- **FR-022**: Если бек-офис на создание брони ответил «временно недоступен» (FR-020), `/book` MUST
  вернуть гостя на страницу квартиры с теми же датами, числом гостей и флагом повторного расчёта
  (как при прочих ошибках брони сейчас) и показать flash-сообщение из `translations.py` (ua и en):
  «Бронювання тимчасово недоступне — спробуйте за N хвилин», где N = `ceil(Retry-After / 60)` при
  допустимом `Retry-After` (FR-020) с правильной формой слова, а иначе вариант без числа
  («…спробуйте трохи пізніше»). Сайт MUST NOT повторять бронь; `/book` по-прежнему идёт мимо
  потолка (FR-010). Журнал — WARNING `book_backoffice_unavailable` с кодом и `Retry-After`, без
  телефона (даже хвоста), имени, дат.
- **FR-023**: Если бек-офис на проверку купона ответил «временно недоступен», ответ гостю MUST
  быть тем же 503 `{"error": "busy"}` (FR-020) — одинаковым для любого телефона, без признака,
  существует ли купон; виджет показывает свою прежнюю строку ошибки купона.
- **FR-024**: Для каталога, квартиры, занятости и цен ответ бек-офиса «временно недоступен» MUST
  приводить к отдаче устаревшего значения из кеша сайта, если оно есть в процессе, независимо от
  его возраста (как сегодня при любом сбое); без него — поведение как при сбое бек-офиса сейчас.

### Key Entities

- **`QUOTE_CACHE_TTL` (T)**: секунды; «не задана»/пусто/0 — выключено; неверное — выключено +
  ERROR; при включении — 30.
- **`BACKOFFICE_MAX_CONCURRENT` (N)**: целое число одновременных обращений на процесс;
  «не задана»/пусто/0 — выключено; неверное — выключено + ERROR.
- **`BACKOFFICE_SLOT_WAIT` (W)**: секунды ожидания места; по умолчанию 2; действует только при
  включённом потолке; неверное — 2 + ERROR.
- **Запись кеша котировки**: ключ (квартира, заезд, выезд, гости) → успешный ответ бек-офиса и
  момент истечения; живёт в памяти одного процесса, не журналируется, купонного телефона не
  содержит; в процессе не больше 2000 записей.
- **Отказ по потолку**: событие «места не было W секунд»; даёт гостю 503 `busy` или прежнее
  значение из кеша и WARNING-запись `backoffice_busy`.
- **Ответ бек-офиса «временно недоступен»**: код 429 или 503 плюс необязательный `Retry-After`
  (целые секунды 1–3600, иначе «нет»); тело не разбирается. Для гостя — как отказ потолка, на брони
  — своё сообщение с минутами; в журнале — `backoffice_unavailable` / `book_backoffice_unavailable`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Без новых настроек все прежние тесты сайта (pytest и Playwright-смока) зелёные, и
  на тестовой серии котировок число обращений к бек-офису равно числу котировок (0 расхождений
  с поведением до фичи).
- **SC-002**: С включённым кешем 100 одинаковых котировок без купона в пределах срока в одном
  процессе дают ровно 1 обращение к бек-офису; 100 котировок с купонным телефоном — ровно 100.
- **SC-003**: С потолком N под нагрузкой, в разы превышающей N, наибольшее число одновременных
  обращений одного процесса к бек-офису (кроме броней) не превышает N ни в одном измерении.
- **SC-004**: При занятом потолке гость получает ответ не позже чем через W + 0,5 с — ни один
  запрос не висит до таймаута обращения (10 с).
- **SC-005**: Замер на подмене с задержкой бек-офиса 350 мс и 50 одновременными котировками
  (конфигурация сервиса `-w 3 --threads 12`) до и после включения показывает: пиковое число
  одновременных обращений к подмене не выше «процессы × N», а при одинаковом ключе число
  обращений к подмене падает не меньше чем в 10 раз; результаты — p95, доля 503, число обращений
  и пик — записаны в `deploy/README.md`.
- **SC-006**: Во всём журнальном выводе тестов фичи — 0 вхождений тестовых адресов гостей,
  купонных телефонов, номеров броней, а в новых записях фичи — и дат.
- **SC-007**: При бек-офисе в режиме техработ (503 + `Retry-After: 300`, HTML или JSON-тело) на
  всех путях US5 гость получает описанный ответ в 100 % тестовых случаев: бронь — сообщение «за 5
  хвилин» с сохранёнными датами и гостями и 0 повторных обращений к бек-офису; JSON-ручки — 503
  `busy` с `Retry-After: 300`; страницы с прогретым кешем — 200.

## Assumptions

- Ёмкость бек-офиса — 50 одновременных котировок на весь сайт (его замер 11.09, «Контекст»);
  значения по умолчанию — «выключено»; T = 30 с и W = 2 с — рекомендуемые при включении, N —
  по расчёту «⌊50 / процессы⌋», только когда процессы × потоки > 50.
- Собственный лимит бек-офиса на `/api/public`, если появится, ответит 429 или 503; иной код
  потребует правки FR-020 (придёт через дирижёра).
- Котировка не зависит от языка интерфейса (сайт не передаёт язык в запрос котировки), поэтому
  язык в ключ кеша не входит; plan проверяет это по коду.
- Котировка без купонного телефона не зависит от гостя: ответ одного гостя можно отдать другому.
  Если бек-офис считает частоту анонимных котировок по адресу гостя, кеш уменьшит число таких
  обращений — это не нарушение, а цель.
- Все обращения к бек-офису уже идут через `api_client.py`; фича не добавляет новых вызовов.
- Сервис на машине переходит на `-w 3 --threads 12` отдельным заданием; фича от этого не
  зависит, но рекомендуемые значения считает для этой конфигурации.
- Входит: `api_client.py`, `config.py`, `app.py` (ответы гостю при отказе и «временно
  недоступен», реакция `/book`), `translations.py` (строки сообщения брони, ua и en), `tests/`,
  `deploy/README.md`, `deploy/site.env.example`, `e2e/fake_transport.py`, `e2e/fake_wsgi.py` и
  `e2e/test_fake_transport.py` (только FR-021).
- Вне фичи: бек-офис; `static/main.js`, шаблоны; логика оплаты, форма брони и сбор 48; прочий
  `e2e/` (смоку и замер только запускать); `wsgi_adapter.py`, `infra/`; включение настроек на
  машине и на Lambda.
- В спеке, тестах и примерах — только синтетика: телефоны вида `+380000000000`, адреса из
  документационных диапазонов (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32).
